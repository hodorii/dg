# Requirements — bpmn-yaml

## 정의
코드펜스에 손으로 BPMN 프로세스를 쓰는 사용자가 장황한 BPMN XML 대신 짧은 YAML로 같은 그림을 얻을 수
있도록, `bpmn-xml`이 표준 충실도를 검증한 BPMN 의미 모델을 그대로 옮긴 dg 자체 YAML 스키마를 새 외부
의존성 없이 읽어 이미 있는 BPMN 렌더링(검증·레인 배치·도형 어휘)으로 그리는 두 번째 BPMN 입력 문법
기능이다. YAML은 XML의 **대안 직렬화**다 — 모델 형태를 바꾸지 않고, XML 문서와 같은 내용의 YAML 문서는
같은 그림이 된다.

## Boundary Context
- **In scope**: `bpmn` 코드펜스·확장자 없는 입력에서 BPMN YAML 문서의 판별(본문 스니핑), YAML 블록 스타일
  하위집합(블록 매핑·블록 시퀀스·평문/홑따옴표/겹따옴표 스칼라·`#` 주석·임의 폭 공백 들여쓰기)의 읽기,
  참여자(풀)·중첩 레인·소속·제목·방향, 노드 두 표기(압축형 `id: 종류 이름`, 확장형 매핑), 종류·트리거
  어휘(BPMN XML 로컬 요소명 그대로 — XML 문법과 같은 표 하나), 경계 이벤트 부착, default 흐름 지정, 흐름
  한 줄 표기(mermaid 화살 문법 재사용: `-->` 시퀀스·`-.->` 메시지/데이터 연관·`-.-` 연관·라벨 두 형태),
  손상·범위 밖 입력에 대한 패닉 없는 원문 코드블록 폴백, 기존 XML 입력과 mermaid·PlantUML 렌더링 불변,
  같은 내용의 XML 문서와 그림 동일성, 예시 문서의 외부 YAML 도구 유효성 검증
- **Out of scope**: 완전한 YAML 1.2(앵커/별칭·태그·다중 문서·흐름 매핑/시퀀스 `[]`/`{}`·블록 스칼라
  `|`/`>`·복합 키 `? `·암묵 타입 변환 — 모두 거부 또는 문자열 유지, 사용자 결정 2026-09-25),
  `.yaml`/`.yml` 확장자에 의한 판별(범용 YAML 파일을 BPMN으로 오판할 수 없으므로 본문 스니핑만), 종류·트리거의
  짧은 별칭(`message` 등 — 표준 로컬 이름만), 노드 안에 흐름을 적는 표기·흐름 사슬(`a --> b --> c`)·흐름 id
  지정, 펼친 서브프로세스·`Group`·조건식·문서화, 새 도형·표식·검증 규칙, 진단 메시지 UI(실패는 기존과 같이
  원문 코드블록), `biz-process.md` 문법(`bizprocess-bpmn`), `examples/` 예제 문서 추가(검증용 문서는 테스트
  전용 자산으로만, `examples/` 밖 — 미구현 기능에 examples 앵커 금지 관례)

## Acceptance Criteria

### 1. 입력 판별
- 1.1: [`bpmn` 코드펜스 본문의 들여쓰기 없는 줄(주석·빈 줄 제외)이 전부 `title`·`orientation`·`participants`·
  `nodes`·`flows` 중 하나를 키로 하는 `키:` 줄이고, 그중 `participants`·`nodes`·`flows`가 하나 이상 있음] →
  [BPMN YAML로 판별돼 그림이 그려진다]
- 1.2: [`bpmn` 코드펜스 본문이 BPMN XML(`bpmn-xml` 1.1)] → [이 기능 이전과 같이 XML로 판별·렌더링된다]
- 1.3: [본문이 스키마 밖 YAML(`process:\n  id: p1`)·`biz-process.md` 조각(`## L1 …`)·평문·빈 문자열] → [BPMN으로
  판별되지 않고 원문 코드블록으로 물러난다(이 기능 이전과 동일)]
- 1.4: [확장자·코드펜스 언어가 없는 입력(표준 입력·`.txt`)이 1.1의 문서] → [BPMN으로 판별돼 그림이 나오고
  PlantUML 등 다른 언어로 오판되지 않는다]
- 1.5: [파일 확장자가 `.yaml`·`.yml`] → [확장자만으로는 BPMN으로 판별되지 않고 본문 스니핑(1.1) 결과를 따른다]
- 1.6: [항상 + mermaid·PlantUML 소스] → [언어 판별 결과가 이 기능 이전과 동일하다]

### 2. YAML 표면 문법(블록 스타일 하위집합)
- 2.1: [같은 문서를 들여쓰기 폭 2/4/혼합(수준마다 다른 폭)으로 쓴 것] → [세 문서의 그림이 동일하다]
- 2.2: [값이 평문·홑따옴표(`''`로 따옴표 이스케이프)·겹따옴표(`\"`·`\\`·`\n` 이스케이프) 스칼라] → [노드 이름에
  따옴표가 벗겨진 본문이 보이고, `\n`은 라벨의 둘째 줄이 된다]
- 2.3: [따옴표 밖 `#`부터 줄 끝까지의 주석, 주석만 있는 줄, 빈 줄, 줄 끝 공백] → [없는 문서와 그림이 동일하다]
- 2.4: [따옴표 안의 `#`·`:`·`-`] → [주석·키·시퀀스로 해석되지 않고 이름 본문에 그대로 보인다]
- 2.5: [값이 `true`·`007`·`1.0`·`null`·`~`처럼 다른 타입으로 보이는 평문] → [문자열 그대로 이름에 보인다(암묵 타입
  변환 없음)]
- 2.6: [`키:` 뒤에 값이 없고 다음 줄이 더 깊이 들여쓰인 블록] → [그 블록이 값이다]; [더 깊은 블록도 없음] → [빈
  문자열 값(이름 없는 노드·레인)이다]
- 2.7: [문서 첫 줄이 `---`] → [무시되고 나머지가 정상 읽힌다]
- 2.8: [앵커(`&a`)·별칭(`*a`)·태그(`!!str`·`!x`)·흐름 컬렉션(`[a, b]`·`{k: v}`)·블록 스칼라(`|`·`>`)·복합 키(`? `)·
  둘째 문서 구분(`---`·`...`)이 어디든 있음] → [패닉 없이 원문 코드블록으로 물러난다]
- 2.9: [탭 들여쓰기·어떤 열린 수준과도 맞지 않는 들여쓰기·같은 매핑의 중복 키·같은 수준에 `- 항목`과 `키: 값`
  혼재·닫히지 않은 따옴표·`키:` 없는 평문 줄] → [패닉 없이 원문 코드블록으로 물러난다]
- 2.10: [중첩 깊이가 64를 넘는 문서] → [패닉·스택 넘침 없이 원문 코드블록]

### 3. 문서 구조 → 풀·레인·소속·제목·방향
- 3.1: [`participants:` 시퀀스의 항목이 `id:` 한 키에 `name:`·`nodes:`를 가진 매핑, 둘 이상] → [참여자 이름의 풀
  띠가 선언 순서대로 그려지고 그 안에 자기 `nodes:`의 노드가 놓이며 캡션이 `◈ bpmn · collaboration`이다]
- 3.2: [참여자 항목의 값이 스칼라(`- customer: 고객`)] → [노드 없는 빈 띠와 제목이 그려진다(블랙박스 풀)]
- 3.3: [참여자 안 `lanes:` 시퀀스, 레인 안 다시 `lanes:`(하위 레인)와 `nodes:`] → [부모 띠 안에 자식 띠가 선언
  순서대로 중첩되고 노드는 자기를 품은 가장 안쪽 레인 안에 놓인다]
- 3.4: [참여자 항목에 `lanes:`와 `nodes:`가 함께 있음] → [`nodes:`의 노드는 풀 직속(레인 밖)에 놓인다]
- 3.5: [`participants:` 없이 최상위 `nodes:`·`flows:`만] → [띠 없는 평면 그림이고 캡션이 `◈ bpmn · process`다]
- 3.6: [`title: 주문 처리`] → [그림 제목이 `주문 처리`다]; [`title` 없음] → [제목이 없다]
- 3.7: [`orientation: horizontal` / `vertical` / 없음] → [풀 띠가 위아래로 쌓임 / 좌우로 나란함 / 위아래(기본)]; [그
  외 값] → [원문 코드블록]
- 3.8: [`orientation: vertical` + 명령줄 방향 옵션] → [명령줄 옵션이 문서 값을 덮는다(기존 규약)]
- 3.9: [최상위·참여자·레인·노드의 매핑에 스키마 밖 키(`nodes` 대신 `elements`, 노드의 `label`)] → [원문 코드블록]

### 4. 노드 표기 → 도형(기존 어휘 표 그대로)
- 4.1: [압축형 `- review: userTask 주문 검토`(값 = 종류 토큰 + 공백 + 이름)] → [`«user»` 둥근 상자 `주문 검토`]
- 4.2: [압축형 값이 종류 토큰만(`- start: startEvent`)] → [이름 없이 그려진다(이벤트는 위치 글자만·게이트웨이는
  기호만)]
- 4.3: [확장형(값이 매핑: `kind:` 필수, `name:`·`trigger:`·`attached_to:`·`default:` 선택)] → [압축형과 같은 규칙으로
  그려지되 선택 필드가 반영된다]; [`kind:` 없음] → [원문 코드블록]
- 4.4: [종류 토큰이 BPMN XML 로컬 요소명 — `startEvent`/`intermediateCatchEvent`·`intermediateThrowEvent`/
  `endEvent`, `task`·`userTask`·`serviceTask`·`scriptTask`·`manualTask`·`businessRuleTask`·`sendTask`·`receiveTask`,
  `subProcess`·`adHocSubProcess`·`transaction`, `callActivity`, `exclusiveGateway`·`parallelGateway`·
  `inclusiveGateway`·`complexGateway`·`eventBasedGateway`, `dataObjectReference`·`dataStoreReference`,
  `textAnnotation`] → [같은 토큰의 XML 요소와 같은 도형·라벨(`○`/`◎`/`◉`, `«user»`…, `[+]`, `«call»`,
  `×`·`+`·`○`·`*`·`◎`, `«data»`/원통, 점선 상자)]
- 4.5: [`trigger:`가 `messageEventDefinition` … `parallelMultipleEventDefinition`(12종)인 이벤트] → [둘째 줄
  `«message»` … `«parallelMultiple»`]; [이벤트가 아닌 노드의 `trigger:`] → [원문 코드블록]
- 4.6: [`kind: boundaryEvent` + `attached_to: <활동 id>`] → [호스트 활동 옆 다음 층에 중간 이벤트로 놓이고 점선으로
  이어지며(기존 근사), 어느 레인에 적었든 호스트와 같은 레인에 있다]; [`boundaryEvent`에 `attached_to` 없음] →
  [원문 코드블록]
- 4.7: [게이트웨이·활동 노드의 `default: <대상 노드 id>`] → [그 노드에서 그 대상으로 가는 시퀀스 흐름의 꼬리에
  `╱`가 그려진다]; [그런 시퀀스 흐름이 없음] → [원문 코드블록]
- 4.8: [종류 토큰이 표에 없음(`UserTask`·`user`·`gateway`) 또는 트리거 토큰이 표에 없음(`message`)] → [원문
  코드블록(대소문자 그대로 정확 일치만)]
- 4.9: [시퀀스 항목이 단일 키 매핑이 아님(`- startEvent`·`- a: x` 와 `b: y` 두 키)] → [원문 코드블록]
- 4.10: [같은 id의 노드·참여자·레인이 둘] → [기존 검증 규칙대로 거부돼 원문 코드블록]

### 5. 흐름 한 줄 표기 → 선
- 5.1: [`flows:` 항목 `a --> b`] → [실선 화살, 라벨 없음]
- 5.2: [`a -- 예 --> b` 또는 `a -->|예| b`] → [실선 화살에 라벨 `예`]
- 5.3: [`a -.-> b`, 양끝이 흐름 노드] → [점선 + `○` 꼬리 + 열린 화살촉(메시지 흐름)]
- 5.4: [`a -.-> b`, 한쪽 끝이 `dataObjectReference`/`dataStoreReference` 노드] → [데이터 객체와 활동 사이 점선 +
  열린 화살촉(방향은 쓴 그대로)]
- 5.5: [`a -.- b`] → [점선 무표식(연관)]
- 5.6: [화살이 `==>`·`<-->`·`o--o`·`--x`·`---`처럼 위 세 꼴 밖] → [원문 코드블록]
- 5.7: [항목에 화살이 없음·id와 화살 사이 공백 없음(`a-->b`)·끝이 둘 넘음(`a --> b --> c`)·화살 뒤에 남는 글] →
  [원문 코드블록]
- 5.8: [`flows:` 항목이 문자열이 아님(매핑·시퀀스)] → [원문 코드블록]
- 5.9: [흐름 끝이 문서에 없는 id·풀을 넘는 시퀀스 흐름·풀 안 메시지 흐름] → [기존 검증 규칙대로 거부돼 원문
  코드블록]
- 5.10: [한쪽 끝이 최상위 참여자 id인 `-.->`] → [그 풀 띠에 닻을 둔 메시지 흐름으로 정상 렌더링된다(XML 5.5와 같음)]

### 6. 손상 입력 강건성
- 6.1: [문서가 줄 중간·블록 중간에서 잘림] → [패닉 없이 원문 코드블록 또는(잘린 뒤가 그 자체로 유효하면) 그림]
- 6.2: [빈 문자열·공백만·주석만·`---`만] → [패닉 없이 원문 코드블록]
- 6.3: [1.1의 판별은 통과하지만 본문 어디선가 2.8~2.9·3.9·4.3~4.9·5.6~5.8 위반] → [패닉 없이 원문 코드블록]
- 6.4: [1.1~6.3의 어떤 입력 + 폭 8·20·40·80·200] → [패닉이 없다]
- 6.5: [마크다운 문서 안 `bpmn` YAML 펜스의 파싱이 실패함] → [그 펜스만 코드블록이 되고 앞뒤 문단은 정상 렌더링
  된다]; [성공함] → [`◈ bpmn · …` 캡션의 그림이 문단 사이에 놓인다]

### 7. 회귀·동일성·실물 확인
- 7.1: [항상 + mermaid·PlantUML 코드펜스] → [렌더링 결과가 이 기능 이전과 바이트 단위로 동일하다]
- 7.2: [항상 + `bpmn-xml`의 XML 예시 문서(주문 처리 협업)] → [렌더링 결과가 이 기능 이전과 바이트 단위로 동일하다]
- 7.3: [항상] → [외부 의존성이 늘지 않는다(의존성 4개 그대로)]
- 7.4: [`bpmn-xml` 7.3의 주문 처리 협업을 같은 노드·흐름 순서로 옮긴 YAML 문서(풀 `고객`·`판매사`, 레인 `영업`·
  `창고`, `«message»` 시작, `«user»`/`«service»` 태스크, `×` 게이트웨이 + `default:`, 경계 `«error»` 이벤트,
  `-.->` 메시지 흐름, `-- 예 -->` 라벨)] → [노드·흐름 수가 XML 문서와 같고 폭 100 렌더링 결과가 XML 문서의
  것과 텍스트 단위로 동일하며 `○ ◉ ◎ «user» «service» «message» «error» × ╱ ╌`가 모두 보인다]
- 7.5: [7.4 문서와 2.x·3.x·4.x·5.x 검증용 YAML 문서 전부] → [외부 YAML 파서(설치된 것: `python3` PyYAML;
  `yq`는 미설치)가 오류 없이 읽고, 읽은 구조(키·순서·시퀀스 길이)가 dg가 읽은 것과 같다 — 위 스키마가 유효한
  YAML임을 기계 검증(research.md 미검증 항목 해소)]
