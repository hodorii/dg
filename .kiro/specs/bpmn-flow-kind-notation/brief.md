# 브리프: bpmn-flow-kind-notation

## 문제
터미널에서 BPMN 협업 다이어그램을 읽는 dg 사용자가 시퀀스 흐름, 메시지 흐름(사용자 표현 "event flow"), 데이터 흐름(데이터 연결과 연결)을 선만 보고 구분하지 못한다. 사용자 요청 원문: "event flow, data flow, sequence flow 를 구분할 수 있게".

## 현황
- 흐름 종류 -> 선 대응은 `src/diagram/bpmn/lower.rs` `line_for()` 한 곳이다 (cited: 코드). `bpmn-model` design.md 117~118행 표와 requirements 3.3~3.5가 이 대응을 정했다 (cited).

  | 흐름 | 선 | 꼬리 | 머리 |
  |---|---|---|---|
  | 시퀀스 | 실선 `─` | 없음 | 채운 화살촉 `▶` |
  | 메시지 | 점선 `╌` | `○` | 열린 화살촉 `>` |
  | 데이터 연결 | 점선 `╌` | 없음 | 열린 화살촉 `>` |
  | 연결 | 점선 `╌` | 없음 | 없음 |

- 이 세션에서 네 종류를 한 다이어그램에 렌더링해 보니 메시지와 데이터 연결은 선과 머리가 같고 출발 쪽 `○` 하나로만 구분된다. 선 가운데만 보면 둘을 가를 수 없다 (cited: 세션 렌더링).
- 캔버스 선 종류는 `Solid`, `Dashed`, `Heavy` 셋뿐이다(`src/diagram/canvas.rs` `LineKind`, `line_char()`). 잔 점선 종류가 없다 (cited: 코드).
- 같은 렌더링의 가로(LR) 배치에서 태스크 -> 주석(`textAnnotation`) 연결선이 태스크 바로 옆에서 다른 선과 겹쳐 `╭──╮╌┬┬╌┌╌╌┐`처럼 이음 글자가 겹친 채 그려진다. 세로(TB) 배치에서는 같은 선이 정상이다 (cited: 세션 렌더링, `-.-` 연결).
- 빈 삼각형 머리 `Marker::Triangle`(`△ ▽ ◁ ▷`)은 이미 있고 PlantUML 상속 표기가 쓴다(`plantuml/relation.rs`) (cited: 코드).

## 목표 상태
사용자가 정한 표기대로 흐름 세 갈래가 선과 머리만으로 구분된다.
- 시퀀스: 실선 + 채운 머리 (그대로).
- 메시지: 빈 동그라미 꼬리 + 대시선 `╌ ╎` + 빈 삼각형 머리 `▷` (상속 화살표 모양).
- 연결(association): 잔 점선 `┈ ┊`, 머리 없음.
- 데이터 연결(data association): 잔 점선 `┈ ┊` + 화살표 머리.
- 가로 배치에서도 연결선이 다른 선과 겹치지 않고 한 줄로 이어진다.

## 접근
캔버스에 잔 점선 선 종류(`Dotted`)를 하나 더하고, `line_for()` 대응표를 위 목표로 바꾼다. 머리는 기존 표식(`Triangle`, `OpenArrow`)을 다시 쓰므로 새 글자는 점선 두 개뿐이다. 다른 접근(머리만 바꾸고 선은 그대로)은 선 가운데에서 여전히 구분되지 않아 사용자가 기각했다.

## 범위
- **포함**: 캔버스 잔 점선 선 종류(직선, 교차, 모서리 이음 규칙 포함), BPMN 흐름 네 종류의 선과 표식 대응, 이를 기대하는 기존 테스트와 예제 렌더링 갱신, 풀 닻으로 가는 메시지 흐름(별도 배선 경로)에도 같은 표식 적용, 가로 배치 연결선 겹침 결함(재현 후 원인은 설계 단계에서).
- **제외**: XML과 bizprocess의 흐름 종류 판정은 그대로(YAML은 요구사항 단계에서 사용자가 양 끝 대상 기준 자동 선택으로 결정해 포함), 범례 줄, mermaid와 PlantUML 다이어그램의 선 표기, 경계 이벤트를 호스트 테두리에 올리는 배치.

## 경계 후보
- 캔버스 선 종류와 글자 선택(`canvas.rs`): 모든 다이어그램이 공유하는 하위 계층. 새 종류를 더해도 기존 종류의 출력은 바이트 동일해야 한다.
- BPMN 흐름 -> 선 대응(`bpmn/lower.rs` `line_for()`): BPMN 전용 정책.

## 경계 밖
- 흐름 종류를 새로 추가하거나 파서가 흐름 종류를 판정하는 규칙 변경.
- 시퀀스 흐름 표기 변경.

## 상류 / 하류
- **상류**: `bpmn-model`(흐름 종류 모델), `bpmn-pool-lane-rendering-polish`(풀 간선 `draw_pool_edges()`가 표식을 그리는 경로, 미커밋).
- **하류**: `bpmn-notation-refinement`류 표기 정비, 범례 기능(요청 시).

## 기존 스펙 접점
- **확장**: `bpmn-model` requirements 3.3~3.5와 design 대응표(이 스펙이 대체), `bpmn-yaml` requirements 5.3(메시지 흐름 표기 문구), `bpmn-xml`의 같은 표기 문구.
- **인접**: `diagram-crow-foot-orientation`, `diagram-diamond-side-glyph-coverage`(글자 커버리지 규칙의 전례).

## 제약
- 글자는 Noto Sans Mono CJK 커버리지 안이어야 한다. 이 세션 `fc-list` 실측: `┈ ┊ ╌ ╎ △ ▽ ◁ ▷` 모두 커버(각 2) (cited).
- 의존성 4개 유지, 패닉 금지, 레인 없는 다이어그램과 다른 문법의 출력 바이트 동일.
- 모서리 글자는 점선 변형이 없다(`╭ ╮ ╰ ╯`). 지금 대시선도 모서리는 실선 모서리를 쓴다 (cited: `line_char()`).

## 근거
- **찬성 근거**: 메시지와 데이터 연결이 선과 머리가 같아 구분이 안 된다 (cited: 세션 렌더링). 가로 배치 연결선 겹침도 같은 렌더링에서 재현됐다 (cited). BPMN 2.0 표준 표기가 메시지 = 대시선 + 빈 원 + 빈 화살촉, 연결 = 점선, 데이터 연결 = 점선 + 화살촉이다 (assumption: 표준 문서는 이 세션에서 다시 확인하지 않음). 필요한 글자와 빈 삼각형 표식이 이미 있다 (cited).
- **반대 근거**: 폰트에 따라 `┈`(4분할)와 `╌`(2분할)가 비슷해 보일 수 있다 (assumption: 사용자 터미널에서 눈으로 확인 필요). 선 종류 추가는 `LineKind`를 쓰는 모든 `match`에 닿는다 (cited: `LineKind::` 사용처 81곳, 대부분 생성 쪽이라 컴파일러가 빠뜨린 곳을 알려 준다). 같은 칸에서 대시선과 잔 점선이 만나면 어느 쪽 글자를 쓸지 규칙이 필요하다 (assumption).

## 결정
GO - 문제(메시지와 데이터 연결 구분 불가, 가로 배치 연결선 겹침)가 세션 렌더링으로 확인됐고 표기는 사용자가 정했다. 단일 도메인, 작업 약 7~9개로 새 스펙 하나(경로 C)에 맞다. 겹침 결함은 선 표기와 같은 경로를 건드리므로 별도 버그픽스로 나누지 않고 이 스펙에 함께 둔다(사용자 결정).
