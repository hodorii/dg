# Requirements — bizprocess-bpmn

## 정의
이 저장소의 Kiro 방법론으로 `biz-process.md`(L1~L5 계층 + `Logic(AST)`)를 쓰는 사용자가 그 문서를 BPMN
다이어그램으로 볼 수 있도록, 문서의 헤딩 계층을 Sub-Process 드릴다운(Process 1장 + Activity 장들)으로 옮기고
헤딩 끝 괄호의 `participant:` 태그를 레인으로 그리는 세 번째(마지막) BPMN 입력 문법 기능이다. 기존 XML·YAML이
만드는 것과 같은 BPMN 의미 모델을 거쳐 이미 있는 검증·레인 배치·도형 어휘로 그린다. 태그 문법·드릴다운 매핑·
기본 렌더링 정책은 `bpmn-support/research.md` §Design Decisions(사용자 결정)를 그대로 따른다.

## Boundary Context
- **In scope**: `bizprocess` 코드펜스와 `-d`/`--lang bizprocess`/표준입력 입력의 판별(`## L1 …:` 헤딩 스니핑),
  헤딩 계층(`L1`~`L5`, `#` 개수·들여쓰기 무관, 이어지는 줄 합침)·`Logic(AST)` 항목(`IF`/`ELSE IF`/`ELSE`/`THEN`/
  `THROW`·`항상:`·평문)의 읽기, 게이트 줄(`✅ 검토 요청`)·정의·가치사슬 표 등 비구조 줄 무시, 헤딩 끝 괄호 태그
  (ID 목록·`key: value` 목록·`participant:`)와 이름 속 괄호의 구분, 참여자 상속·역할당 레인 하나, L1~L5 →
  풀/Sub-Process/파선 그룹/태스크 매핑, Logic → 게이트웨이·default 흐름·경계 오류 이벤트·텍스트 주석, 렌더링
  정책(`activity` 기본 · `all` · `N`)과 `--depth`/`DG_DEPTH`/소스 지시자, 캡션 `◈ bizprocess · process` /
  `· activity: <이름>` / `· step: <이름>`, 기존 `biz-process.md` 7개 전부의 회귀 렌더링, 손상 입력의 패닉 없는 원문
  코드블록 폴백, 기존 mermaid·PlantUML·BPMN XML·YAML 렌더링 불변, README의 문법·옵션 표 갱신
- **Out of scope**: `biz-process.md` 템플릿·`biz-process-rules.md`의 수정(방법론 트랙 — 이 스펙의 태그 문법은 dg
  쪽 잠정 표준), 확장자 `.md`만으로 다이어그램 판별(마크다운 문서로 여는 동작 불변), 특정 노드만 골라 펼치기·
  페이저 클릭 드릴다운(v1 제외), L5 형제의 병렬 표기(`PAR:` 등 — 순차로만, 병렬은 모델에 여지만), L1 둘 이상이
  메시지로 통신하는 다중 풀 협업, 진단 메시지 화면 표시(`all` 폴백 안내 한 줄 제외 — 나머지 진단은 라이브러리
  API로만), 새 도형·표식(파선 그룹 테두리 한 종류만 추가), `examples/*.md` 추가(회귀 픽스처는 저장소의 실제
  `biz-process.md`와 테스트 전용 fixture만)

## Acceptance Criteria

### 1. 입력 판별
- 1.1: [코드펜스 언어가 `bizprocess` 또는 `biz-process`] → [본문이 이 문법으로 읽혀 그림 또는(실패 시) 원문 코드블록]
- 1.2: [`-d`·표준입력·`--lang bizprocess` 입력의 본문에 `#` 뒤 `L1 <종류>: <이름>` 꼴 헤딩 줄이 있음] → [`bizprocess`로
  판별돼 그림이 나오고 PlantUML 등 다른 언어로 오판되지 않는다]
- 1.3: [`dg <경로>/biz-process.md`(옵션 없음)] → [이 기능 이전과 같이 마크다운 문서로 렌더링된다(헤딩·표 그대로)]
- 1.4: [항상 + mermaid·PlantUML 소스, BPMN XML·YAML 문서] → [언어·갈래 판별 결과가 이 기능 이전과 동일하다]
- 1.5: [`bpmn` 코드펜스 본문이 `## L1 …` 문서] → [이 기능 이전과 같이 BPMN으로 판별되지 않고 원문 코드블록]

### 2. 문서 구조 읽기
- 2.1: [`## L1 Process: A`, `### L2 Activity: B`, `  ### L3 FunctionGroup/UI: C`, `    ### L4 Step: D`, `      ### L5
  DetailStep: E` — 들여쓰기 폭·`#` 개수가 무엇이든] → [레벨은 `L1`~`L5` 토큰으로만 정해지고 `L<n>`과 `:` 사이의
  종류 낱말은 무엇이든 받아들인다]
- 2.2: [헤딩 텍스트가 다음 줄(헤딩·`Logic(AST):`·`- ` 항목·빈 줄이 아닌 줄)로 이어짐] → [한 칸 띄워 합친 뒤 이름·
  괄호 태그를 읽는다(`markdown-gfm-alerts`의 L4 두 줄 헤딩이 한 이름)]
- 2.3: [`### ✅ 검토 요청 (L1: …)` 줄과 그 다음 안내 줄, `## 정의`·`## 가치사슬 매핑`과 표, `#` 없는 설명 문단] →
  [구조에 들어가지 않고 그림에도 나타나지 않는다]
- 2.4: [`Logic(AST):` 줄 아래 `- `로 시작하는 항목들, 항목이 더 깊이 들여쓴 다음 줄로 이어짐] → [항목마다 한 줄로
  합쳐져 직전 헤딩(L5 또는 L4)의 논리로 읽힌다]
- 2.5: [L1 헤딩이 둘 이상] → [L1마다 별도 Process 그림(+ 그 Activity 그림들)이 문서 순서로 이어지고 각 Process 그림의
  제목이 그 L1 이름이다]
- 2.6: [L1 헤딩이 하나도 없음, 또는 L1 아래 L2가 하나도 없음] → [원문 코드블록]
- 2.7: [L5 없는 L4, L3 없는 L2(L4가 L2 바로 아래), L2 아래 아무것도 없음] → [각각 태스크, L2 직속 L4, 자식 없는
  Sub-Process로 그려지고 패닉이 없다]

### 3. 괄호 태그
- 3.1: [헤딩 끝 괄호가 `1.1, 2.3` · `1.1~1.5, 2.1` 같은 ID 목록] → [이름에서 제거되고 그림에 나타나지 않는다]
- 3.2: [헤딩 끝 괄호가 `valueChainRef: VC-…` · `participant: 학습자`처럼 `키: 값`을 쉼표로 이은 목록] → [태그로
  읽혀 이름에서 제거되고, `participant` 이외의 키는 무시된다]
- 3.3: [괄호 내용이 ID 목록도 `키: 값` 목록도 아님(`감시 루프(백그라운드)`, `(표준입력이거나 파일 미지정)`)] →
  [괄호째 이름 텍스트로 남는다]
- 3.4: [헤딩 끝에 태그 괄호가 둘 이상(`… (participant: 멘토) (2.1, 2.3)`)] → [뒤에서부터 파싱되는 괄호는 모두 태그,
  처음 파싱되지 않는 괄호부터는 이름]
- 3.5: [`(participant: 학습자, 멘토)`처럼 `키: 값` 목록의 한 조각에 `:`가 없음(값 안 쉼표)] → [원문 코드블록(값에 쉼표
  불허)]
- 3.6: [`(participant:  학습자 )` · `(participant: 시스템운영자)`와 `(participant: 시스템 운영자)`] → [앞뒤 공백만 제거되고
  대소문자·안쪽 공백은 그대로라 뒤의 둘은 서로 다른 레인이다]
- 3.7: [태그가 L1에만 있음] → [모든 L2~L5가 그 참여자를 상속해 레인 하나만 그려진다]; [L2에 태그, 그 아래 L4에 다른
  태그] → [L2와 다른 L4·L5는 L4의 참여자, 나머지는 L2의 참여자(가장 가까운 조상 상속)]
- 3.8: [같은 역할 이름이 여러 헤딩에 재등장] → [레인은 역할 이름당 하나, 첫 등장 순서로 위에서 아래(가로 흐름 기준)]
- 3.9: [문서에 `participant:` 태그가 하나도 없음(기존 7개 문서)] → [풀·레인 없이 그려지고 캡션이 `◈ bizprocess · process`다]
- 3.10: [태그가 하나라도 있음] → [L1 이름의 풀 띠 안에 역할 레인들이 그려진다]

### 4. 드릴다운 매핑
- 4.1: [Process 그림] → [`○` 시작 → L2들을 문서 순서로 이은 접힌 Sub-Process 상자(`[+]`) → `◉` 종료]
- 4.2: [L2 아래 L3이 하나] → [L3 이름은 그 L2 상자의 둘째 줄(부제)이고 Activity 그림에 그룹 상자가 없다]
- 4.3: [L2 아래 L3이 둘 이상] → [Activity 그림에서 L3마다 파선 테두리 그룹 상자가 그 L3의 L4들을 감싸고 제목이 L3
  이름이며, L3 사이에는 흐름이 그려지지 않는다]
- 4.4: [L4에 L5가 있음 / 없음] → [Activity 그림에서 펼친 상자(제목 = L4 이름) 안에 L5 태스크들이 문서 순서로 이어짐 /
  둥근 태스크 하나]
- 4.5: [L4 형제·L5 형제] → [문서 등장 순서로 실선 화살 순차 연결(병렬 없음)]
- 4.6: [Activity 그림] → [`○` 시작 → L4들 → `◉` 종료, 첫 캡션 `◈ bizprocess · activity: <L2 이름>`]
- 4.7: [이름이 폭을 넘음] → [기존 규약(반대 방향 재시도 → 라벨 축소 → 원문 코드블록) 그대로]

### 5. Logic(AST) → 게이트웨이
- 5.1: [항목에 `IF <조건> THEN <결과>`가 하나 이상] → [소유 L5(또는 L4) 태스크 뒤에 `×` 배타 게이트웨이 하나, 조건마다
  `<조건>` 라벨의 실선 화살이 `<결과>` 이름의 태스크로 간다]
- 5.2: [`ELSE IF <조건> THEN <결과>`] → [같은 게이트웨이의 라벨 있는 갈래 하나 더]
- 5.3: [`ELSE <결과>` 또는 `ELSE (<메모>) THEN <결과>`] → [같은 게이트웨이의 default 흐름(꼬리 `╱`)이 `<결과>`
  태스크로 가고 라벨은 `<메모>`(없으면 없음)]
- 5.4: [`THROW <오류>`(`ELSE THROW …`·`IF … THEN THROW …`)] → [갈래 끝이 `◉ «error» <오류>` 종료 이벤트이고, 그 L5를
  품은 L2 상자에 `«error» <오류>` 경계 이벤트가 붙어 Process 그림에서도 보인다]
- 5.5: [`IF` 없는 항목(`항상: …`, 평문 설명)] → [소유 태스크에 점선으로 이어진 텍스트 주석 상자 한 개에 항목마다 한
  줄]
- 5.6: [게이트웨이가 달린 L5 뒤에 다음 L5 형제] → [다음 L5는 소유 태스크에서 직접 이어지고(갈래는 안에서 끝남) 합류
  게이트웨이는 생기지 않는다]
- 5.7: [`IF`는 있으나 `THEN`이 없는 항목] → [주석 줄로 취급되고 진단이 남는다(그림은 그려진다)]
- 5.8: [항목·헤딩의 결과·조건 텍스트 끝 ID 괄호(`(6.1)`)] → [3.1과 같이 제거된다]

### 6. 렌더링 정책
- 6.1: [옵션 없음(기본 `activity`)] → [Process 그림 1장 + L2마다(자식 있는 것만) Activity 그림 1장씩이 캡션으로 구분돼
  한 블록에 위아래로 이어진다]
- 6.2: [`--depth 0`] → [Process 그림 1장만]; [`--depth 1`] → [한 장에 L2를 펼친 상자로, L4 Sub-Process는 접힘];
  [`--depth 2` 이상] → [L4까지 펼침]
- 6.3: [`--depth all` + 어떤 Sub-Process 안에서도 참여자 전환 없음(태그 없는 문서 포함)] → [전부 펼친 한 장]
- 6.4: [`--depth all` 또는 `--depth N`(N ≥ 1) + 어떤 L2 안에서 참여자가 바뀜] → [`activity` 정책으로 자동 폴백하고 첫
  그림 위에 폴백 사유 한 줄(`※ depth=all 불가(참여자 전환) → activity`)이 보인다]
- 6.5: [`activity` 정책 + 어떤 L4 안에서 참여자가 바뀜] → [그 L4는 Activity 그림에 접힌 상자로, 그 안은 별도 그림
  `◈ bizprocess · step: <L4 이름>`으로 이어진다]
- 6.6: [`--depth` 값이 `all`·`activity`·음이 아닌 정수 밖] → [명령줄 오류로 비제로 종료]; [환경변수 `DG_DEPTH`] →
  [명령줄 옵션이 없을 때 같은 값으로 쓰인다]; [소스 안 `<!-- dg: depth=all -->` 또는 `%% dg: depth=all`] → [명령줄
  값을 덮는다(기존 지시자 규약)]
- 6.7: [`--direction tb`] → [모든 그림이 세로 배치, 풀 띠는 좌우로(기존 방향 옵션 규약)]
- 6.8: [파선 그룹의 L4들이 서로 다른 레인] → [그룹 상자는 생략되고 L4들은 각자 레인에 그려진다]

### 7. 회귀·강건성·실물 확인
- 7.1: [`.kiro/specs/{dg-watch-mode, gitgraph-branch-distinction, gitgraph-junction-polish, markdown-gfm-alerts,
  markdown-link-navigation, markdown-source-view, sequence-fragment-frame-distinction}/biz-process.md` 전부를
  `bizprocess`로 폭 100 렌더링] → [모두 그림이 나오고, L2 수 = Activity 그림 수, `감시 루프(백그라운드)`가 이름에
  괄호째 남고, `검토 요청`·`valueChainRef`·`VC-DG-`·ID 괄호가 어떤 그림에도 없다]
- 7.2: [`dg-watch-mode` 문서] → [Process 그림에 L2 5개 접힌 상자, "감시 모드를 켠다" Activity 그림에 `×`·`╱`·`--watch`
  조건 라벨 셋 중 하나가 보인다]
- 7.3: [빈 문자열·공백만·헤딩 없는 평문·L1만 있고 L2 없음·헤딩 중간에서 잘린 문서·`Logic(AST):`만 있고 항목 없음·
  `- IF` 항목만 있고 헤딩 없음] → [패닉 없이 원문 코드블록 또는(잘린 뒤가 유효하면) 그림]
- 7.4: [7.1·7.3의 모든 입력 + 폭 8·20·40·80·200 + `--depth 0/1/2/all/activity`] → [패닉이 없다]
- 7.5: [마크다운 문서 안 `bizprocess` 펜스의 파싱이 실패] → [그 펜스만 `╭─ bizprocess ` 코드블록이 되고 앞뒤 문단은
  정상]; [성공] → [`◈ bizprocess · process` 캡션의 그림이 문단 사이에 놓인다]
- 7.6: [항상 + mermaid·PlantUML 코드펜스, BPMN XML fixture, BPMN YAML fixture] → [렌더링 결과가 이 기능 이전과 바이트
  단위로 동일하다]
- 7.7: [항상] → [외부 의존성이 늘지 않는다(4개 그대로)]
- 7.8: [`dg -d .kiro/specs/dg-watch-mode/biz-process.md`, `cat <같은 파일> | dg -d`, `dg -d -l bizprocess <파일>`] → [셋 다
  `◈ bizprocess · process`로 시작하는 그림]
- 7.9: [README] → [지원 문법 표에 `bizprocess` 행, 옵션 표에 `--depth`·`DG_DEPTH`, `-l`의 값 목록에 `bpmn`·`bizprocess`]
