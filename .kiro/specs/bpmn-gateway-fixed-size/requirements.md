# Requirements — bpmn-gateway-fixed-size

## 정의
BPMN 그림에서 게이트웨이를 이름 길이와 무관하게 한눈에 같은 도형으로 알아보려는 사용자를 위해,
게이트웨이 마름모의 크기 정책을 "내용 적응형(현행)"으로 둘지 "고정 크기 + 기호만 안 + 이름은 밖
(bpmn.io 관례)"으로 바꿀지 실물 비교(`research.md`·`render-comparison.md`)를 근거로 결정하고, 어느
결론이든 그 수용 기준을 확정하는 기능이다. 두 갈래 (a)·(b) 중 하나만 채택된다 — 선택은 승인 시
오케스트레이터·사용자가 한다.

## Boundary Context
- **In scope**: BPMN 게이트웨이 다섯 종류(배타 `×`·병렬 `+`·포괄 `○`·복합 `*`·이벤트기반 `◎`) 노드의
  크기, 기호 위치, 이름 위치, 간선 접점 위치, 출구 라벨 가시성 — 위→아래·왼쪽→오른쪽, 레인 안팎,
  이름 없음·짧음·두 줄 줄바꿈, 입구·출구 여럿 모두; 협업 예제(`examples/bpmn.md` 둘째 블록)의 결과;
  갈래 (b)일 때 "현행 유지" 결론과 근거의 기록
- **Out of scope**: mermaid `{}` 판단 노드·상태도 `<<choice>>`·PlantUML diamond 등 게이트웨이가 아닌 마름모의
  모양(회귀 기준으로만 등장 — 1.1); 게이트웨이 기호 다섯 글자 자체(`bpmn-shapes` 완료); 이벤트·태스크·
  서브프로세스 표기; 간선 라벨·통로·교차 규칙 일반(게이트웨이 출구 라벨 소실 2.8만 이 스펙 책임); 색상;
  `examples/*.md` 파일 추가·수정; 점 고정 노드가 층에서 가장 넓을 때 흐름선이 왼쪽으로 꺾이는 기존
  특성(이벤트에 이미 있음, 2.11은 허용만 명시)
- **Adjacent expectation(design 단계 예고)**: 갈래 (a)는 그리기(`layout::shape`)만이 아니라 배치기
  (`layout::graph`)의 접점·정렬 기준까지 바꾸는 결정이다 — 이벤트가 쓰는 `Shape::is_point_anchored`
  술어(소비 지점: 정렬 중심, 접점 모음, 접점 벌림 제거, 접점 밀기 제외)를 게이트웨이로 넓혀야 하고,
  이벤트(접점 = 원점 글자)와 달리 마름모의 접점은 원점에서 떨어진 중심 칸이라 술어를 "방향별 오프셋"으로
  일반화해야 함이 프로토타입에서 확인됐다. 그 파급 범위(소비 지점별 전제 재검증, 왼쪽→오른쪽 라벨 소실의
  원인)는 design에서 다룬다. 공유 도형(마름모)을 직접 바꾸지 않고 BPMN 전용 도형을 두는 경로가 1.1을
  지키는 방법으로 확인됐다(`research.md`).

## 비교 근거(발췌 — 원문·전체 표본은 `render-comparison.md`)
표본 1(위→아래) 세 게이트웨이: 짧은 이름 `OK?`, 긴 이름(자동 두 줄), 이름 없음. 현행:
```text
 ╱───────╲
‹  × OK?  ›
 ╲───────╱
```
```text
 ╱────────────────────────────╲
‹  + 모든 사전 준비가 끝난 뒤  ›
‹             병합             ›
 ╲────────────────────────────╱
```
```text
              ╱───╲
             ‹  ○  ›
              ╲───╱
```
후보 B(고정 5×3 + 기호 안 + 이름 오른쪽 가운데 줄) 같은 세 노드:
```text
    ╱─╲
   ‹ × › OK?
    ╲─╱
```
```text
 ╱─╲
‹ + › 모든 사전 준비가 끝난 뒤
 ╲─╱  병합
```
```text
    ╱─╲
   ‹ ○ ›
    ╲─╱
```
왼쪽→오른쪽 분기(표본 4) — 현행은 두 출구 라벨이 다 보이지만, 점 고정 후보 A·B·C는 `예`가 사라진다:
```text
         ‹                ›─예──────╮
○ 주문──▶‹  × 재고 있음?  ›         │
         ‹                ›─아니오─╮╰▶
```
```text
○ 주문──▶‹ × › 재고 있음?─아니오─┬▶‹ + › 병렬 분기──┬┬╮
```
후보 A(기호 한 글자만)는 이름 없는 포괄 게이트웨이가 시작 이벤트와 같은 `○` 한 글자가 되어 구분이
불가능하다(표본 1 후보 A) — 실물로 기각 근거가 확보된 후보. 후보 C(이름 아래)는 위→아래에서 이름이
마름모와 흐름선 사이에 끼고, 왼쪽→오른쪽에서 마름모와 출구 선 사이에 이름 폭만큼 빈틈이 생긴다(표본 1·2).

## Acceptance Criteria

### 1. 공통 — 어느 갈래든
- 1.1: [항상 + 게이트웨이가 없는 BPMN 그림, mermaid `{}` 판단 노드·상태도 `<<choice>>`·PlantUML diamond를
  쓰는 그림] → [렌더링 결과가 `cbfd774` 시점과 바이트 단위로 동일하다]
- 1.2: [항상] → [게이트웨이 렌더링에 쓰이는 글자는 기호 다섯(`×`·`+`·`○`·`*`·`◎`)과 마름모 글자
  (`╱`·`╲`·`‹`·`›`·`─`)뿐이며 모두 기본 CJK 모노 폰트 커버리지 안(`bpmn-shapes/research.md` 실측)이다 — 새
  글자를 들이지 않는다]
- 1.3: [이름 없음·한 글자·긴 이름(두 줄 줄바꿈)·출구 3개·입구 3개·레인 안·위→아래·왼쪽→오른쪽의 어떤
  조합] → [패닉 없이 렌더링된다]
- 1.4: [갈래 확정] → [채택한 갈래와 그 근거(실물 표본 번호)가 `research.md` Design Decisions에 기록된다]

### 2. 갈래 (a) — 고정 크기 채택 시
- 2.1: [게이트웨이 노드, 이름 길이·유무 무관] → [마름모가 항상 폭 5·높이 3(`╱─╲` / `‹ 기호 ›` / `╲─╱`)이다]
- 2.2: [다섯 종류 각각] → [기호가 마름모 가운데 칸에 하나만 있고, 마름모 안에 다른 글자가 없다]
- 2.3: [이름 있는 게이트웨이] → [이름이 마름모 밖에, 승인 시 확정한 한 방향(B: 오른쪽 가운데 줄 / C: 아래
  첫 줄)에 놓이고, 한 그림 안 모든 게이트웨이가 같은 방향을 쓴다 — **결정 필요 ①**]
- 2.4: [이름 없는 게이트웨이] → [5×3 마름모만 그려지고 이름 자리 여백이 남지 않는다]
- 2.5: [이름이 폭 상한을 넘어 두 줄로 줄바꿈됨] → [마름모는 5×3 그대로이고 둘째 줄은 이름 첫 줄 바로 아래
  같은 시작 열에 온다]
- 2.6: [위→아래, 입구·출구 간선이 몇 개든] → [모든 선·화살촉이 마름모 위·아래 꼭짓점 열(가운데 열)의 바로
  바깥 칸에 닿는다 — 이름 길이와 무관]
- 2.7: [왼쪽→오른쪽, 입구·출구 간선이 몇 개든] → [모든 선·화살촉이 마름모 가운데 줄(기호 줄)에 닿는다]
- 2.8: [출구가 둘 이상이고 각 출구에 라벨(예·아니오 등)이 있음, 위→아래·왼쪽→오른쪽 모두] → [라벨이 하나도
  소실되지 않고 각 갈래 선 위에 읽히게 놓인다(프로토타입 왼쪽→오른쪽의 `예` 소실은 불합격)]
- 2.9: [이름 없는 `○`·`◎` 게이트웨이와 시작·중간 이벤트가 한 그림에 있음] → [마름모 테두리 유무로 한눈에
  구분된다]
- 2.10: [`examples/bpmn.md` 둘째 블록(주문 처리 협업)] → [폭 100 안에서 `× 재고 있음?` 게이트웨이가 5×3
  마름모 + 밖 이름으로 창고 레인 안에 그려지고, `예`·`아니오` 라벨이 둘 다 보이며, 게이트웨이 외 요소의
  글자는 그대로다]
- 2.11: [이름이 길어 층에서 가장 넓은 게이트웨이(위→아래)] → [앞선 노드에서 오는 선이 왼쪽으로 꺾여
  들어와도 마름모 가운데 열에 닿는다(꺾임 자체는 이벤트와 같은 기존 특성으로 허용)]

### 3. 갈래 (b) — 현행(내용 적응형) 유지 시
- 3.1: [항상] → [모든 BPMN 그림의 렌더링 결과가 `cbfd774` 시점과 바이트 단위로 동일하다(코드 변경 없음)]
- 3.2: [결론 기록] → [기각 근거(표본별 후보 A·B·C의 한계: 이벤트 글자 충돌, 왼쪽→오른쪽 라벨 소실, 이름
  끼임·빈틈)가 `research.md`에 남고 로드맵 2번 항목이 "현행 유지" 결론으로 닫힌다]
- 3.3: [후속 기록] → [점 고정 노드의 왼쪽→오른쪽 다중 출구 라벨 소실이 이벤트에도 잠재하는 배치기 한계로
  별도 스펙 후보에 기록된다(이 스펙은 고치지 않음)]
